High — verified Floating chat button blocks taps on the Roadmap's Daily Mission buttons

src/components/shell/fab-chat.tsx · src/pages/roadmap.tsx · src/features/roadmap/components/roadmap-view.tsx

On a signed-in student's Roadmap page (the normal state once onboarding is done — not an edge case), the floating "KruAI" mentor button sits directly on top of the second Daily Mission row's Done button. I confirmed this isn't just a visual near-miss: document.elementFromPoint() at the center of that button returns the FAB, not the button underneath, so a tap there opens the chat overlay instead of marking the mission done.

Why it happens: FabChat is offset bottom-20 (80px) specifically so it clears BottomNav — its own comment says so ("bottom-20 clears BottomNav"). That math only works on the seven pages that actually render BottomNav. RoadmapPage and ProfilePage render neither BottomNav nor an equivalent spacer, so on those two routes the 80px offset just floats the button in open content instead of above a reserved nav bar. RoadmapView's own pb-36 bottom padding doesn't help — it only creates room once the user has scrolled to the very end of the page; it does nothing to keep the fixed-position FAB off content that scrolls through that same screen region on the way there. I measured this at 360×740 and 375×667 (iPhone SE 2/3) — both show a real overlap, just against different rows (the collision zone is a fixed spot on screen, so which content row lands there depends on the page's total height at that viewport).

Suggested fix

Give FabChat real information about whether a bottom nav is present, rather than assuming it (e.g. a prop from ShellLayout/AppShell, or reading the same condition BottomNav already uses), and fall back to a plain corner offset — the same pattern the component already uses for lg, where it drops to lg:bottom-6 because there's no BottomNav on desktop either. Roadmap and Profile need that same "no nav here" offset on mobile.

Minor — consistency Chat message list is missing min-h-0, unlike every other scroll region in the shell

src/components/shell/chat-overlay.tsx:339

The main message list is flex-1 space-y-3 overflow-y-auto. Every other scrolling flex child in this codebase — AppShell's content column, every page wrapper, SidebarNav, FocusLayout's body, and even this same file's own HistoryPanel list two hundred lines down — pairs flex-1 overflow-y-auto with an explicit min-h-0. This one instance doesn't.

In current evergreen browsers this is mostly harmless: setting overflow-y: auto also computes overflow-x to auto per the CSS overflow spec, and a flex item with non-visible overflow on an axis gets an automatic minimum size of 0 on that axis — which is exactly what min-h-0 would have forced. So the list does still shrink and scroll correctly today. It's worth aligning anyway: it's the one inconsistency in an otherwise very disciplined pattern, and the math field panel below it can claim up to ~330px of height on a short/landscape viewport, which is exactly the scenario where an older WebKit build (some Android WebViews still lag current Chrome) could disagree with the newer spec behavior and let the list's content push the composer off-screen instead of scrolling internally.

// chat-overlay.tsx:339 — missing min-h-0
<div className="mx-auto w-full max-w-2xl flex-1 space-y-3 overflow-y-auto px-4 pb-3">

// compare HistoryPanel two hundred lines later, in the same file:
<div className="mx-auto w-full min-h-0 max-w-2xl flex-1 overflow-y-auto p-3">

Architecture note Up to three independently-scrolling containers stacked per screen

src/components/shell/app-shell.tsx · every file under src/pages/ · src/components/shell/focus-layout.tsx

AppShell wraps every route's content in its own min-h-0 flex-1 overflow-y-auto. Most individual pages (home.tsx, game.tsx, progress.tsx, lessons.tsx, leaderboard.tsx, grade-prediction.tsx, exam.tsx) then wrap their own content in a second copy of the same pattern. Screens that use FocusLayout — the mock exam, a lesson, the placement test — add a third layer for the exercise body. Right now every layer is sized correctly (that's exactly why finding 2 above is currently masked rather than visibly broken), so nothing here is failing today. It's flagged because it's the direct root cause of the fragility in finding 2: three layers of "this has to carry min-h-0/flex-1 correctly or the wrong container scrolls" is three chances for a future edit to drop one, versus one chance if AppShell were the sole scroll owner and pages only opted into an extra scroll region (like FocusLayout's) when they genuinely need independent framing.

Checked, no bug Typed commitment signatures don't actually overflow their card

src/features/commitment/components/signature-display.tsx

This looked like a textbook flex-overflow bug on paper: the typed-signature <span className="truncate"> sits inside a plain flex items-center overflow-hidden row with no min-w-0 anywhere in the chain, and the confirmation screen constrains it to a fixed w-56 (224px) box. The classic version of this bug lets long, unbreakable text blow out past its container instead of truncating. I typed a 31-character unbroken name ("Sovannmakarapanharithchanthorn" — longer than any real name is likely to be, and within the field's own maxLength=40) into the actual running app and it truncates correctly everywhere it's used: the live preview while typing, the fixed-width confirmation card, and the persisted Roadmap banner.

The reason it works despite the missing min-w-0: the span itself carries overflow-hidden (part of the truncate utility), and a flex item with non-visible overflow gets an automatic minimum size of zero per the flexbox spec — the same rule that saves finding 2 above. Recorded here so it's clear this was checked in a real browser rather than assumed safe from reading the JSX.

Checked, no bug Dense 4-column stat rows don't clip, even in Khmer at 320px

src/features/home/components/stat-pills.tsx · src/features/progress/components/score-hero.tsx · src/features/game/components/game-stats-card.tsx

These pack an icon, value and an 8–9px label into four grid columns — tight, and Khmer script needs more room than Latin (the codebase's own globals.css notes this for line-height). I rendered StatPills in the Khmer locale at 320px width (the narrowest phone still worth supporting) and measured every label's scrollWidth against its box: nothing clips. Long labels wrap to a second line inside their column instead of overflowing. Not a bug — noted so it's clear the smallest supported width was actually checked in the language most likely to break it, not just assumed fine because English fit.

Methodology

Static reading of every file under src/ (~115 files) surfaced the candidates above. Rather than report them from the JSX alone, I copied the project (via the device bridge) into a scratch environment, ran npm install and the real Vite dev server, and drove it with Playwright/Chromium:

  • Seeded localStorage directly with the shape lib/store.ts's persist config expects, to reach post-onboarding / signed-commitment states without re-driving the login and survey flow each time.
  • Tested at 320×568, 360×740 and 375×667 — the narrowest end of what a Cambodian-market Android/iOS device mix would show.
  • Used getBoundingClientRect() and document.elementFromPoint() to measure actual overlap and actual click-target ownership, not just visual proximity in a screenshot.
  • One limitation: this container has no egress to fonts.googleapis.com, so Noto Sans Khmer never loaded during testing — Khmer glyphs rendered as tofu in my screenshots. That's a test-environment artifact, not a finding; it doesn't affect the layout/overflow measurements above, which read computed box sizes rather than rendered glyph shapes.
